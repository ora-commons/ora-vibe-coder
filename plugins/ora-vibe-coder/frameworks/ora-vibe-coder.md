# Ora Vibe Coder

## Purpose

Guide the complete fixed lifecycle while preserving the independent contracts of Specification, Planning, Programming, and Verification. Current truth lives in the conversation, retained artifacts, actual project files, current check output, and Git state—not in a runner, progress file, receipt, or state service.

Use this framework with the complete [shared contract](../references/shared-contract.md), its required role-and-assignment source, and all four stage bodies below. Portable packets supply all those texts, with the role catalogue exactly once. Accept an idea, partial work, or an existing project without requiring Ora provenance.

The actual stage instructions are [Ora Specification](ora-specification.md), [Ora Planning](ora-planning.md), [Ora Programming](ora-programming.md), and [Ora Verification](ora-verification.md). Read the complete relevant body before using a stage. A prepared guided packet includes this guide, shared rules, and all four complete bodies so they are available when needed. They are the same canonical instructions used independently, not summaries or host-specific variants. Having them available does not authorize running every stage.

Staff a project coordinator when coordination is needed, using that role from the shared catalogue. For small work, the existing self-contained workflow may own the assignment without an extra coordinator. Name document custody in either case. A staffed coordinator commissions substantive work and reads returned evidence; it never becomes a spare executor, product tester, verifier, or substantive document author.

## Find the real starting point

Establish the starting state from current conversation, accessible artifacts, code, documentation, check evidence, findings, and Git state. A staffed coordinator delegates substantive inspection and reads the returned evidence. Determine the earliest incomplete or invalid stage by substance:

1. **Specification** — product intent is complete, materially reviewed, shown in full, and approved by the user.
2. **Planning** — the real project was inspected; the HOW is executable, materially reviewed, shown in full, and approved by the user.
3. **Programming** — the released Programming Loop reached its approved finish line; actual code, three truthful documentation products, checks, review, delivery, and cleanup meet the Plan.
4. **Verification** — one fresh independent reviewer cumulatively inspected the entire current candidate and all authorized checks pass with no material finding.
5. **REPORT** — the certifying artifact describes that exact passed candidate.

Also identify the agreed completion endpoint and any delivery or cleanup still outstanding. A passed stage or REPORT does not erase that work.

Do not infer readiness from a filename, file existence, old status, prior claim, or harness. Explain the earliest useful stage, what is missing, and the likely consequence. This is advisory: when the user explicitly accepts weak upstream quality, record the reduced basis and continue as far as the remaining stage contracts truthfully allow. A missing required companion cannot be overridden.

## Run the fixed lifecycle

Use the selected stage's actual canonical body and give each fresh recipient one complete clean handoff under the shared context table. A native entry may load it when genuinely available. Otherwise show a complete manual handoff, what to open, what to paste, and the expected next result. Do not assume native commands, hidden sibling context, or automatic delivery. Preparation or copying alone does not advance a stage. Do not reproduce a stage's method here or build a configurable stage graph.

Dispatch the Plan's ready assignments through the host mechanism described in the shared contract. Supply each role, selected skill, complete assignment, current accepted sources, dependency boundary, and return owner in the actual request. Keep ownership and material progress in existing project records with the designated custodian. Start independent unowned work, join results at agreed review boundaries, and hold only affected dependencies. Receive direct handbacks and resume workers with accepted changes; do not make the user relay routine messages or replace useful context with a consultant's entire debate.

### 1. Specification

Assign an executor Ora Specification with the user's idea, current Request, existing requirements, and material corrections. Preserve interactive Request updates and establish project-specific completion and retained/delegated decisions. Show the complete current Specification and separate review status, then obtain explicit user approval before normal downstream use.

### 2. Planning

Assign an executor Ora Planning with the current Request, approved Specification, project path, instructions, and inspected facts. Require assignments, dependencies, foundation review, and the whole delivery route. Exclude rejected designs and Gear transcripts. Show the complete current Plan and separate review status, then obtain explicit user approval before Programming.

### 3. Programming

Commission the Programming Loop owner through Ora Programming with the approved Specification and Plan, role source, complete assignment, actual project state, and protected-work facts. Exclude raw Request history, planning discussion, and Gear deliberation. The Loop owns scope approval, internal workers, exact checks, independent review, verdicts, correction, Git finish line, documentation, recovery, single independent supervision, and cleanup. Receive its inspectable candidate and evidence; create no second execution or monitoring lane.

### 4. Verification

Commission Verification through its owner with the complete candidate: Specification, Plan, product, three documentation products, authorized check output, and relevant baseline or diff. The owner assigns a separate verifier under Ora Verification. Exclude raw Request and implementation transcript. Verification remains read-only toward the candidate; only its optional overview field and REPORT after PASS are writable under normal artifact authority.

### 5. Certification

Have the authorized worker create REPORT only through the Verification contract after `PASSED` applies to the complete current candidate. The artifact certifies that exact candidate and is not itself proof.

Never auto-advance after silence. Each stage stops at its own boundary, and Specification and Plan approval are separate user decisions.

## Route correction to the earliest owner

Treat every material Verification finding as correction work:

- Missing or wrong WHAT returns to an executor using Specification; follow accepted correction with affected Planning, Programming, and fresh cumulative Verification.
- A changed or invalid HOW returns to an executor using Planning; follow accepted correction with affected Programming and fresh cumulative Verification.
- Code or documentation that violates adequate upstream artifacts returns to Programming, followed by fresh cumulative Verification.

Send the owner one consolidated current finding set and controlling artifacts/evidence, excluding superseded findings. Apply the shared amendment route: appropriate authorship, required review and acceptance, incorporation by document custody, and notification/refresh before affected workers resume. Delegated detail needs no automatic user interruption; changed goals, constraints, reserved decisions, or effects do. Preserve initial stage approvals and each self-contained workflow's correction procedures. Repeat affected authorized downstream work and fresh whole-candidate review. Continue while correction makes progress; never turn an unresolved finding into a REPORT limitation.

## Finish or stop truthfully

After PASS and REPORT, assign any remaining authorized finishing work to its responsible workers through the existing delivery procedure. Obtain evidence that the agreed output exists at its intended location and final condition, with required documentation and cleanup complete. Resolve any material difference introduced by delivery through the applicable owner and verification before claiming completion. Remove only task-owned temporary material no longer needed; preserve user files, other tasks, and companion qualification records.

End with either a necessary user decision/intervention or a substantive completion notice naming what was delivered, where to inspect it, verification evidence, and fulfilled delivery/cleanup obligations. A retained approval request shows the ready result, decision needed, remaining work, and next action; continue independent authorized work. Do not call a review checkpoint or paused project complete.

Silence, resumption, and explicit abandonment follow the shared contract. In particular, unresolved findings can end only as `CLOSED BY USER — UNRESOLVED FINDINGS`, with no REPORT and no claim of completion, verification, readiness, or success.
