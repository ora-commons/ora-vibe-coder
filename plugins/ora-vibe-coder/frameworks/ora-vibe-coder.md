# Ora Vibe Coder

## Purpose

Help the user turn an idea into software by offering useful structure, document standards, AI assistance, and verification, while the user decides which tools and stages to use. Current truth lives in the conversation, retained artifacts, actual project files, current check output, and Git state—not in a runner, progress file, receipt, or state service.

- Use this framework with the complete [shared contract](../references/shared-contract.md), its required role-and-assignment source, and all four stage bodies below.
- Portable packets supply all those texts, with the role catalogue exactly once.
- Accept an idea, partial work, or an existing project without requiring Ora provenance.
- The actual stage instructions are [Ora Specification](ora-specification.md), [Ora Planning](ora-planning.md), [Ora Programming](ora-programming.md), and [Ora Verification](ora-verification.md). Read the complete relevant body before using a stage.
- A prepared guided packet includes this guide, shared rules, and all four complete bodies so they are available when needed. They are the same canonical instructions used independently, not summaries or host-specific variants. Having them available does not authorize running every stage.
- Staff a project coordinator when coordination is needed, using that role from the shared catalogue. For small work, the existing self-contained workflow may own the assignment without an extra coordinator. Name document custody in either case.
- A staffed coordinator commissions substantive work and reads returned evidence; it never becomes a spare executor, product tester, verifier, or substantive document author.

## All stages remain available

The user may create a Plan with an incomplete or missing Specification, start programming with an incomplete or missing Plan, and ask questions, inspect code, import material, and revise documents at any time. They may request verification using whatever requirements and implementation evidence is available. No document's completeness, review result, approval record, or fingerprint controls permission to proceed, and no warning, acknowledgement, waiver, or bypass mode replaces that freedom.

- Ask useful questions and explain consequential gaps during the normal conversation. If the user chooses to proceed with the available information, do so and report the resulting limitations honestly.
- Establish the current state from conversation, accessible artifacts, code, documentation, check evidence, findings, and Git state. A staffed coordinator delegates substantive inspection and reads the returned evidence.
- Explain what stage would be most useful, what is missing, and the likely consequence. This is advice for the user's decision, never a gate.
- Do not infer readiness from a filename, file existence, old status, prior claim, or harness. An unavailable optional companion (Gear, Bridge) is disclosed and worked around, never demanded.

## Run the lifecycle the user chooses

- The user's workspace may resolve documents automatically — a deliberate association first, then the expected name, a recognized `vibe_document` type label, then role words in the filename, newest within a rank. Revision requests name the resolved displayed file, an explicit file choice overrides discovery, external saves appear when the user rereads the files, and discovery never proves completeness.
- The user's workspace ordinarily talks with the selected coding tool in its own conversation: one submitted message at a time, carried by the bundled Agent Bridge, with the project documents visible and refreshed beside it. Stage boundaries apply there exactly as everywhere else.
- The prepared packet is the portable and terminal-recovery route. Use the selected stage's actual canonical body and give each fresh recipient one complete clean handoff under the shared context table.
- A native entry may load that handoff when genuinely available; otherwise show a complete manual handoff, what to open, what to paste, and the expected next result.
- Do not assume native commands, hidden sibling context, or automatic delivery; preparation or copying alone does not advance a stage.
- Do not reproduce a stage's method here or build a configurable stage graph.
- Dispatch the Plan's ready assignments through the host mechanism described in the shared contract. Supply each role, selected skill, complete assignment, current accepted sources, dependency boundary, and return owner in the actual request.
- Keep ownership and material progress in existing project records with the designated custodian.
- Start independent unowned work, join results at agreed review boundaries, and hold only affected dependencies.
- Receive direct handbacks and resume workers with accepted changes; do not make the user relay routine messages or replace useful context with a consultant's entire debate.

### 1. Specification

Assign an executor Ora Specification with the user's idea, current material, existing requirements, and corrections; for existing software, direct the executor to inspect relevant accessible code when a location is known. Preserve interactive updates and establish project-specific completion and retained/delegated decisions. Show the complete current Specification. A fresh independent assessment of whether it sufficiently guides the intended work is available on request; its COMPLETE or INCOMPLETE verdict is advisory information for the user, never a gate.

### 2. Planning

Assign an executor Ora Planning with the current Request, the available Specification, project path, instructions, and inspected facts. Require assignments, dependencies, foundation review, and the whole delivery route. Exclude rejected designs and Gear transcripts. Show the complete current Plan; its assessment verdict is advisory information, never a gate on programming.

### 3. Programming

Commission programming through Ora Programming with the available Specification and Plan, role source, complete assignment, actual project state, and protected-work facts. When the Programming Loop companion is present it owns scope approval, internal workers, exact checks, independent review, verdicts, correction, Git finish line, recovery, supervision, and cleanup; without it, the receiving session implements directly under its normal approvals and says so. Receive its inspectable candidate and evidence; create no second execution or monitoring lane. The Loop saves a truthful Programming Result after actual work.

### 4. Verification

Commission Verification through its owner with the accessible candidate: available Specification and Plan, product, any documentation, authorized check output, and relevant baseline or diff. The owner assigns a separate verifier under Ora Verification. Exclude raw Request and implementation transcript. Verification remains read-only toward the candidate; its writable outputs are the Verification Report and its optional overview field. The report is saved for passing, failing, and incomplete reviews alike, with a truthful verdict; the displayed verdict comes from the saved report, and neither its existence nor an older passing result proves newer code passed.

### 5. Delivery

After verification, assign any remaining authorized finishing work through the existing delivery procedure. The Verification Report's readiness conclusion informs that work; it is not itself proof.

Never auto-advance after silence. Each stage stops at its own boundary; a technical review PASS and the user's separately recorded approval are distinct facts, and neither substitutes for the other.

## Route correction to the earliest owner

Treat every material Verification finding as correction work:

- Missing or wrong WHAT returns to an executor using Specification; follow accepted correction with affected Planning, Programming, and fresh cumulative Verification.
- A changed or invalid HOW returns to an executor using Planning; follow accepted correction with affected Programming and fresh cumulative Verification.
- Code or documentation that violates adequate upstream artifacts returns to Programming, followed by fresh cumulative Verification.

Send the owner one consolidated current finding set and controlling artifacts/evidence, excluding superseded findings. Apply the shared amendment route:

- appropriate authorship;
- required review and acceptance;
- incorporation by document custody; and
- notification/refresh before affected workers resume.

For every correction:

- Delegated detail needs no automatic user interruption; changed goals, constraints, reserved decisions, or effects do.
- Preserve initial stage approvals and each self-contained workflow's correction procedures.
- Repeat affected authorized downstream work and fresh whole-candidate review.
- Continue while correction makes progress; record any unresolved finding truthfully in the Verification Report instead of converting it into a final limitation.

## Finish or stop truthfully

After a passing Verification Report:

- Assign any remaining authorized finishing work to its responsible workers through the existing delivery procedure.
- Obtain evidence that the agreed output exists at its intended location and final condition, with required documentation and cleanup complete.
- Resolve any material difference introduced by delivery through the applicable owner and verification before claiming completion.

Cleanup:

- Remove only task-owned temporary material no longer needed; preserve user files, other tasks, and companion qualification records.

Ending:

- End with either a necessary user decision/intervention or a substantive completion notice naming what was delivered, where to inspect it, verification evidence, and fulfilled delivery/cleanup obligations.
- A retained approval request shows the ready result, decision needed, remaining work, and next action; continue independent authorized work.
- Do not call a review checkpoint or paused project complete.

Silence, resumption, and explicit abandonment follow the shared contract. In particular, unresolved findings can end only as `CLOSED BY USER — UNRESOLVED FINDINGS`, with a truthful not-passed Verification Report and no claim of completion, verification, readiness, or success.
